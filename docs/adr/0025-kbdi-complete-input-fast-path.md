# KBDI complete-input fast path: reordered within the parity tolerance

## Status

Accepted. A measured exception to {doc}`ADR-0017 <0017-rust-core-acceleration-backend>`
decision 4 ("a port reproduces the Python numerics — operation order …"), for one
kernel path. The implementation is `crates/climate-indices/src/kbdi_fast.rs`,
`crates/climate-indices/src/kbdi_exp_table.rs` (generated by
`scripts/generate_kbdi_exp_table.py`), and `complete_input` in
`crates/climate-indices/src/fire.rs`.

## Context

The native KBDI kernel was slower than xclim's numba kernel. On GitHub's Linux runners
it took 2–2.6× xclim's time on a 2500-cell grid. Two costs dominate, and neither can be
removed while every operation keeps the Python reference's order:

- **A single series is one serial dependency chain.** Each day evaluates
  `(203.2 − Q1) · heat / den · 1e-3` on the index: about thirty cycles of dependent
  arithmetic, including a divide. The temperature factor
  `heat = 0.968 exp(0.0875 T + 1.5552) − 8.30` does not depend on the index, but in that
  order it sits between the index and the next day.
- **On a grid, `exp` dominates.** The platform `exp` is a library call that does not
  vectorize. Its result also differs between platforms (glibc, the Windows C runtime and
  macOS round differently), so the native output was never platform-independent.

Most real input is complete: every day observed, every cell usable, no fire season.
Under that contract, `recurrence::run` never poisons, bridges or carries a cell, so a run
is just the daily step applied to every cell on every day.

## Decision

1. **Complete input takes a separate path; everything else keeps the driver bit for
   bit.** `fire::kbdi` routes a run to `kbdi_fast::run` when every condition holds:
   - every day is observed and every cell is usable;
   - there is no season mask;
   - every climatology is finite with a finite denominator;
   - every carried state is finite, with the index at most 203.2 mm;
   - both weather views are in standard layout. The driver reads a strided or
     column-major view in place, where the fast path would have to copy both grids.

   Two more conditions are checked inside the run, folded into a running sum of the
   inputs: every precipitation and temperature value is finite, and every temperature is
   at most 7000 °C. From about 8030 °C the driver's `(203.2 − Q1) · heat` overflows to
   infinity and caps the index at 203.2 mm, an order of operations the reordered
   fraction does not reproduce. A run that fails either check is recomputed by the
   driver, which gives the same result as checking the inputs first.
2. **The drying fraction leaves the dependency chain.**
   `k = max(heat · 1e-3 / den, 0)` (0 below 10 °C) is computed per cell-day from inputs
   alone. The index step becomes `Q = min(203.2, Q1 + (203.2 − Q1) k)`. The wet-spell
   arithmetic keeps its operations and order, so the carried wet-spell total stays
   bit-identical.
3. **`heat` comes from a table-driven `exp`, not the platform's.**
   - `0.968` is folded into the argument as `+ ln 0.968`.
   - The argument is reduced as `x = (m + j/256) ln 2 + r`, with `|r| ≤ ln 2 / 512`.
   - `2^(j/256)` comes from a 256-entry table, each value correctly rounded and
     generated by the checked-in script; a degree-4 polynomial supplies `exp(r) − 1`.
   - There is no fused multiply-add, rounding call or float-to-integer conversion, so
     it vectorizes on the x86-64 SSE2 baseline and on NEON.
   - The heat term has the same bits on every platform. Its error against the platform
     `exp` is below 1e-14 relative from 10 to 80 °C, and below 1e-13 up to the 7000 °C
     limit, where the argument's own rounding dominates. The argument is clamped at
     709, which the limit keeps out of reach.
4. **Eight adjacent cells advance together** in the time-first layout, over tiles of 256
   cells and 32 days, so a tile's lane groups share the pages and cache lines they read.
   Fewer than eight leftover cells (all the cells of a small run) advance together in as
   many lanes; a single series runs the short chain with its state in registers.

## Consequences

- **The native KBDI output changes, within the contract.** Against the previous kernel
  the change is at most 3.3e-13 mm, on the benchmark workloads and on stress inputs:
  cold climates, 40 % rain days, climatologies from 50 to 4000 mm, temperatures of
  ±1e4 °C (a run with a day above 7000 °C now goes to the driver; see decision 1).
  That is well inside `rtol = atol = 1e-10`, and the Python oracle and every native
  parity test hold at that tolerance. Output is no longer bit-identical to 3.0.0 on any
  platform. It is also not fully platform-independent: the heat term is, but each
  cell's climatology denominator still uses the platform `exp`, once per cell, so a run
  can differ across platforms in its last bits.
- **Measured speed.** Single-threaded `fire::kbdi` on Windows ARM64 (Snapdragon X
  Elite), against the bit-identical driver it replaces for complete input:

  | workload | driver | fast path |
  |---|---|---|
  | 1 station, 1825 days | 17.5 µs | 9.4 µs |
  | 1 station, 10958 days | 106.6 µs | 57.0 µs |
  | 400 cells × 3650 days | 14.9 ms | 4.8 ms |
  | 2500 cells × 3650 days | 92.3 ms | 38.2 ms |

  A prototype of the same kernel, run on GitHub's Linux runners, was 1.45–3.0× faster
  than xclim's kernel single-threaded (AMD EPYC 7763 and Arm Neoverse-N2).
- **Two paths to keep in agreement.** Rust tests check the fast path against a
  day-by-day replay of `kbdi_next` at every lane and tile shape, at extreme values, and
  with and without spin-up and recording. They also check that input outside the
  contract stays on the driver bit for bit, including its `NonFinite` error. A change
  to the KBDI step has to land in both `kbdi_next` and `kbdi_fast::step`.
- **A changed constant means regenerating the table** with
  `scripts/generate_kbdi_exp_table.py`. The script and the generated module are
  committed together.

## Alternatives considered

- **Keep the operation order (bit-identical) and only restructure the loops.** The
  fused driver already does this. A single series stays bound by the divide on its
  chain, and a grid by the platform `exp`.
- **A polynomial `exp` with no table.** A branch-free degree-11 Estrin polynomial
  measured about half the speed of the table form on every runner. Its dependency depth
  exceeds what the out-of-order window can overlap.
- **A time-parallel scan for a single series.** The daily map is monotone and
  clamp-affine, so chunks of a series can be composed in lanes. It was faster on Windows
  ARM64 but no faster than the short chain on the Linux runners, so it is not shipped.
- **Checking precipitation and temperature finiteness before the run.** It costs one
  more read of both inputs, about 7 % of a grid run. Folding the check into the run
  gives the same routing.
